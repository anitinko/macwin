# Фаза 4: защищённый рабочий стол Windows — оценка и дизайн

## Итог

Сделать можно. Нужен новый компонент: служба Windows от LocalSystem и процесс-помощник SYSTEM в сеансе пользователя, который вводит события на рабочем столе Winlogon (экран блокировки, UAC, Ctrl+Alt+Del) и в окна программ, запущенных от администратора. Агент пользователя (сеть, ключ, буфер обмена, логика) остаётся как есть.

В этой фазе написан только дизайн, кода нет. Причины:

- компонент с правами SYSTEM — самая чувствительная часть продукта; его нужно проверять на настоящем Windows (экран блокировки, UAC, смена пользователя, RDP), а здесь Windows нет;
- нужны решения владельца: установка с правами администратора в Program Files вместо установки для одного пользователя, подпись кода, включение политики Ctrl+Alt+Del.

## Что не работает сейчас и почему

- **Экран блокировки, вход, запрос UAC.** Они показываются на рабочем столе Winlogon (secure desktop) в WinSta0. Процесс пользователя не может открыть этот рабочий стол. SendInput и низкоуровневые хуки действуют только на рабочем столе своего потока, поэтому ввод с Mac туда не попадает, а мышь PC там не перехватывается.
- **Окна программ, запущенных от администратора.** UIPI не пропускает SendInput из процесса со средним уровнем целостности в окно с высоким. Хуки тоже не видят ввод в таких окнах.
- **Ctrl+Alt+Del.** Через SendInput его не сымитировать. Есть только `SendSAS`, и то если служба или uiAccess-программа разрешены политикой «Disable or enable software Secure Attention Sequence» ([SendSAS][sendsas]).

## Варианты

1. **`uiAccess=true` в манифесте.** Снимает UIPI для окон администратора и разрешает `SendSAS`. Но программа должна быть подписана Authenticode и лежать в `Program Files` или `system32` ([SendSAS][sendsas], [Raymond Chen][uiaccess]), а на рабочий стол Winlogon это всё равно не пускает. Решение частичное.
2. **Весь агент от SYSTEM**, как режим elevate у Barrier и Input Leap: служба запускает клиент с токеном winlogon. Работает везде, но:
   - SYSTEM не может расшифровать ключ в DPAPI пользователя и не видит его буфер обмена;
   - вся сеть и разбор протокола оказываются в процессе SYSTEM;
   - в сентябре 2026 у Input Leap нашли локальное повышение до SYSTEM: служба принимала по `127.0.0.1:24801` команду без аутентификации и запускала её через `CreateProcessAsUser` с токеном winlogon. Исправления нет и не будет ([NotCVE-2026-0015][inputleap]).
3. **Рекомендуемый: разделение на службу, помощника и агента.** Описан ниже.

## Дизайн (вариант 3)

### Компоненты

- **Служба `MacWinInput`** (LocalSystem, автозапуск). Сама ничего не вводит и не слушает сеть. Запускает помощника в активном консольном сеансе и перезапускает его при смене сеанса (`SERVICE_CONTROL_SESSIONCHANGE`, `WTSGetActiveConsoleSessionId`). Порядок запуска:
  - копия собственного токена (`DuplicateTokenEx`);
  - `SetTokenInformation(TokenSessionId)` на нужный сеанс;
  - `CreateProcessAsUser` с `lpDesktop = "winsta0\\winlogon"` ([CreateProcessAsUser][cpau]).
- **Помощник `macwin-input.exe`** (SYSTEM, сеанс пользователя, без сети):
  - следит за входным рабочим столом через `OpenInputDesktop` + `GetUserObjectInformationW(UOI_NAME)`, или подпиской на `EVENT_SYSTEM_DESKTOPSWITCH`, и переводит свой поток туда через `SetThreadDesktop` ([OpenInputDesktop][oid]);
  - выполняет SendInput на текущем входном рабочем столе. Уровень SYSTEM выше любого другого, поэтому ввод доходит и до окон администратора;
  - вторым этапом ставит низкоуровневые хуки на рабочем столе Winlogon, чтобы PC мог управлять Mac и с экрана блокировки;
  - по команде пункта меню «Ctrl+Alt+Del» вызывает `SendSAS(FALSE)`, если политика разрешает это службам ([Chromium remoting][chromium] делает так же).
- **Агент пользователя.** Новый бэкенд `ServiceInjector` (реализует `InputInjector`), а позже и `ServiceCapture`. Если помощник недоступен, используется нынешний `WinInjector`. В остальном агент не меняется.

### Канал агент — помощник

- Именованный канал `\\.\pipe\macwin-input-<SID>`. Его создаёт помощник с DACL «SYSTEM + SID пользователя активного сеанса» и флагом `PIPE_REJECT_REMOTE_CLIENTS`.
- Помощник проверяет клиента:
  - `GetNamedPipeClientProcessId` → `QueryFullProcessImageNameW`: это `macwin-tray.exe` или `macwin.exe` из каталога установки;
  - тот же сеанс (`ProcessIdToSessionId`).
- Протокол — только команды ввода из `macwin-core`: `InjectCommand`, команды grab/release и `SendSas`. Фиксированные protobuf-сообщения с лимитом длины и ограничением частоты.
- Никаких командных строк, путей к файлам и флагов «elevate». Именно на этом сломался Input Leap.

### Установка

- Служба запускает бинарник от SYSTEM, поэтому он должен лежать там, куда пользователь не может писать: `C:\Program Files\MacWin`. Иначе пользователь подменит exe и получит SYSTEM. Нынешняя установка в `%LOCALAPPDATA%` для этого не годится.
- Значит, нужен установщик с правами администратора: `install.ps1 -System` или MSI. Он регистрирует службу (`New-Service`), ставит права на каталог и правила брандмауэра. Режим для одного пользователя без службы остаётся как сейчас.
- Подпись Authenticode желательна: SmartScreen, доверие к службе. Для варианта uiAccess она обязательна.
- Включение политики SoftwareSASGeneration (`HKLM\Software\Microsoft\Windows\CurrentVersion\Policies\System`, значение 1 = службы) меняет безопасность машины. Установщик должен спрашивать, по умолчанию не включать.

### Поведение

- **Блокировка (Win+L).** Агент пользователя продолжает работать, сеть остаётся. Мышь и клавиатура Mac вводят пароль на экране блокировки через помощника.
- **UAC.** Запрос на рабочем столе Winlogon работает так же.
- **Выход из системы и вход после перезагрузки** не поддерживаются: агент пользователя завершён, а его ключ в DPAPI пользователя. Для этого понадобятся отдельная идентичность машины (DPAPI машины) и отдельное сопряжение. Это следующий шаг, не эта фаза.
- **Буфер обмена** на рабочем столе Winlogon не передаётся.

### Безопасность

- Новая возможность: машина, с которой выполнено сопряжение, может вводить пароль на экране блокировки PC. Модель доверия та же (пир и сейчас печатает в сеансе пользователя), но расширенная. Поэтому только по явному согласию: флаг установщика и `secure-desktop = on` в конфиге, по умолчанию выключено.
- Помощник SYSTEM минимален: без сети, без разбора файлов, только проверенные сообщения из канала.
- Служба не принимает команд вообще: она только перезапускает помощника.

## Объём работ

| Часть | Оценка |
|---|---|
| Служба (`StartServiceCtrlDispatcherW`, `RegisterServiceCtrlHandlerExW`, запуск помощника в сеансе) | ~400 строк |
| Помощник (смена рабочего стола, SendInput, хуки, сервер канала с проверкой клиента) | ~600 строк |
| Агент (`ServiceInjector`, `ServiceCapture`, пункт «Ctrl+Alt+Del», настройка) | ~300 строк |
| Установщик с правами администратора и удаление | ~150 строк |
| Тесты: протокол, проверка клиента, логика выбора бэкенда — автоматически; остальное вручную | — |

Итого примерно 1,5–2 недели вместе с ручной проверкой на Windows 10 и 11.

## Ручная проверка (после реализации)

1. Win+L на PC, управление с Mac: ввод PIN или пароля, разблокировка.
2. Запрос UAC (например, `regedit`), ответ мышью и клавиатурой Mac.
3. Окно программы от администратора: ввод с Mac работает.
4. Пункт «Ctrl+Alt+Del» при включённой политике; при выключенной — понятная ошибка.
5. Смена пользователя и вход через RDP: помощник переезжает в новый сеанс, старый канал закрыт.
6. Подмена клиента канала: посторонний процесс того же пользователя получает отказ.
7. Аварийная комбинация на экране блокировки отпускает всё.

## Что решить владельцу

- Нужна ли работа до входа в систему (после перезагрузки).
- Сертификат для подписи кода.
- Ставить ли MacWin для всех пользователей в Program Files (нужно для службы).
- Разрешать ли установщику включать политику Ctrl+Alt+Del.
